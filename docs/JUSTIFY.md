# JUSTIFY: выравнивание текста по ширине — как устроено и что делать, если «слетит»

Актуализировано: 2026-10-12 (релиз 1.3.4, vc52). Прежний разбор — `docs/AUDIT.md` §7.

## TL;DR

- Выравнивание живёт в двух местах: **читалка стиха/лекции** (`HtmlText.kt`, компонент `HtmlText` → `JustifyTextView`) и **списки стихов** (`JustifiedPreviewText` в `HtmlText.kt`, вызов в `ChapterScreen.kt:verseItems` — общий для `ChapterScreen` и `ReaderScreen`).
- На **ColorOS** (OPPO/OnePlus/Realme/POCO) стоковая оправка фреймворка молча не работает; приложение принудительно ставит `justificationMode = NONE` и рисует строки **само** (ручная доводка в `JustifyTextView`). На остальных прошивках — стоковый `INTER_WORD`.
- Если выравнивание «сломалось»: **сначала проверь, где именно** (список vs читалка) и **сравни debug-сборку с release** — в 1.3.0 менялся только способ сборки (debug→release), код оправки с 1.2.38 не менялся (проверено дизассемблированием APK).

## Как реализовано

### Общий каркас (`HtmlText.kt`)

- `HtmlText(...)` → `AndroidView` с `JustifyTextView` (private class в том же файле).
- `isColorOs()` (`HtmlText.kt`, ~стр. 640): `Build.MANUFACTURER` содержит OPPO/OnePlus/Realme/POCO.
- При `justify && !center` на ColorOS: `breakStrategy = SIMPLE`, `justificationMode = NONE`, `hyphenationFrequency = NONE` — **стоковую оправку выключаем сознательно**, место ей занял ручной проход.
- `hyphenationFrequency = NONE` на ColorOS — не случайность: фреймворковый перенос там рвёт слова **без дефиса** («ука зывает»). На стоке — `FULL`.
- Межстрочность (`lineSpacing`) **не трогаем**: RU-locale 0.0 на API 35+ растягивает строки, на API <35 — фолбэк 1.15.

### Ручная доводка (`JustifyTextView`)

- `onDraw`/`draw`: `super` рисует стоковую строку, затем `paintManual` **стирает её фоном** и перерисовывает **пословно** с равными зазорами: `extra = ширина_строки − getLineWidth`, `add = extra / (слов−1)`.
- `lineSegs(line)` — сегменты строки: слова + вычисленные `x0/x1/stockX0`. Возвращает `null` (нет оправки) если: последняя строка абзаца, слов < 2, `extra < 1f`, **или `add > 2×ширина_пробела**` (ограничение дыр, добавлено в 1.3.4 — см. ниже).
- Выделение: `hasRealSelection()` (не collapsed-курсор), `paintManual` красит выделение в **растянутых** координатах и возвращает `true` из `draw()` (гасит Editor-оверлей с stock-координатами, который перебил бы доводку). Проход в `onDraw` **и** в `draw()` — на разных прошивках окно Editor-a рисует в разных местах.
- Тачи: `transformForJustify`/`mapToStock` переводят x в стоковые координаты до `super.onTouchEvent` — ссылки/курсор попадают туда, куда показывает стоковый layout.
- Сноски/ссылки: `VerseLinkMovementMethod` (свой ACTION_DOWN/UP с long-press-guard), `NoteActionMode` (порядок меню выделения).

### Списки стихов (`JustifiedPreviewText`, с 1.3.4)

- Композабл в `HtmlText.kt`: на ColorOS — `AndroidView` с тем же `JustifyTextView` (текст кладётся как `SpannableString`: `lineSegs` работает только с `Spanned`, обычная String вернула бы null); на остальных — Compose `Text(fontFamily = ReadFont, textAlign = ...)`.
- Выделение **не включается** — long-press строки списка (меню «Скопировать/В избранное») остаётся за Compose.
- Отступ `Modifier.fillMaxWidth()` обязателен: без него TextView меряется по контенту и нечего растягивать.

### Ограничение дыр (1.3.4)

Оправка тянет только пробелы; в строке с 2–3 словами зазор выходил в полэкрана. В `lineSegs`: если `add > spaceW * 2` — строка остаётся рваной справа. Одно правило на читалку и список. Если зазор окажется великоват/мелковат — крутится одна константа (`HtmlText.kt`, `lineSegs`).

## Переносы (почему их нет)

Ручной Knuth-Plass (1.2.29–1.2.33) откатили в 1.2.36: он без словаря переносов рвал слова по буквам/склеивал. Фреймворковый перенос на ColorOS выключен (рвёт без дефиса). Единственный честный путь — **мягкий дефис U+00AD, вставляемый только в рендер-копию** (поиск/копирование не трогать): строки тогда рвёт сам `StaticLayout`, рисуя дефис как обычный символ. Не реализовано.

## Что бывает «сломанным» и как разбираться

Симптом → что проверить:

1. **Оправки нет в списке главы, но есть в читалке** → так и было всегда до 1.3.4 на ColorOS (список шёл через Compose-оправку, которую прошивка гасит). Проверить, что установлена версия ≥ 1.3.4 (vc52).
2. **Дыры на переносах** → порог `add > spaceW * 2` в `lineSegs` — подкрутить константу.
3. **Оправки нет вообще, нигде** → сначала откатить подозрение с приложения:
   - **debug-vs-release:** собрать/поставить debug-APK (`gradlew assembleDebug`, подпись та же, данные сохраняются). Debug работает, release нет → виновата сборка (R8/shrink): добавить `-keep class * extends android.widget.TextView { *; }`, выяснять что именно режет R8.
   - **delta-апдейт:** сравнить sha256 **установленного** APK с каталогом (`catalog.json` → `apk.sha256`). Не сошёлся — битый bsdiff-патч, поставить полный APK.
   - **прошивка:** `adb shell getprop ro.build.display.id` — ColorOS перевыпускает текст-стек (в 1.3.x подтверждено: PLG110, ColorOS 16.0.10.501, Android 16 / API 36). Ручная оправка держится на инвариантах фреймворка (порядок отрисовки `onDraw`/`draw`, поведение `getLineWidth`/`getPrimaryHorizontal`/`getLineVisibleEnd`); при смене прошивки они могут поехать. Тут правится сам проход (самопроверка как в 1.2.33 или замеры вместо `getLineWidth`).
4. **Прыгает при выделении** — регрессия к поведению 1.2.34: смотреть `draw()`/`hasRealSelection()`/`paintManual` в `JustifyTextView`.

## Замер на ColorOS 16 (PLG110, Android 16 / API 36) — что выяснилось 13.10.2026

Диагностика в `lineSegs` (временный лог, снят, в коде его нет) на тексте лекции
(`textSize=73.6`, `target=1178`, `spaceW=23`) дала:

| строка | слов | `getLineWidth` | свои замеры | `stock − own` | вердикт |
|---|---|---|---|---|---|
| 'деле в материальном мире' | 4 | 1087 | 1064 | **23** | STRETCH |
| 'на самом деле. И на само' | 6 | 1075 | 1052 | **23** | STRETCH |
| 'Никогда нельзя думать, ч' | 4 | 1122 | 1099 | **23** | STRETCH |
| 'предыдущего. И когда ' | 3 | 912 | 889 | **23** | RAGGED (дыра) |
| 'что эта прадхана – это ' | 5 | 910 | 887 | **23** | RAGGED |
| 'может давать энергии. ' | 3 | 932 | 909 | **23** | RAGGED |

**`stock − own = 23.0 = spaceW` на ВСЕХ строках без исключения.** То есть
`Layout.getLineWidth()` включает в ширину строки **хвостовой пробел разрыва**
(он реально есть в тексте строки — в сниппетах видно «...мире », «...когда »),
а нарисованные чернила заканчиваются на ширину пробела раньше. Отсюда:

- **Оправленные строки не доходили до правого поля на ширину пробела (23px).**
  Правка (1.3.5): запас считается по собственным замерам слов
  (`inkW = сумма ширин слов + промежутки между ними`), а не по `getLineWidth()`.
  Проверка на скриншоте: до правки оправленные строки кончались на x≈1194–1200
  при поле x≈1218 — ровно этот разрыв.
- **«Дыры» в строках с 2–3 словами — не баг, а следствие жадного разрыва.**
  Строка 'предыдущего. И когда ' имеет 3 слова и 266px запаса: 133px на зазор —
  дыра вчетверо шире пробела. Тянуть нельзя, оставляем рваной (порог
  `add > spaceW * 2`).
- **Слово «распространения,» в строку выше не влезает по ширине — это верно.**
  Замерено по пикселям: строка кончалась на x=531, слово шириной 686px, места
  оставалось 665px — не хватало ~21px, слово физически не помещалось. Взять его
  на предыдущую строку можно только переносом (hyphenation), а он на ColorOS
  ломает слова без дефиса (см. ниже).

Итог: **на ColorOS 16 ломается не разрыв, а расчёт запаса** — строки короче
поля на один пробел. Переносы (hyphenation) остаются нерешёнными: фреймворковый
на ColorOS рвёт слова без дефиса, свой — откачен в 1.2.36.

## Что НЕ является причиной (проверено)

- **Релизная сборка 1.3+ (R8, shrinkResources, подпись)**: код оправки в релизном APK семантически идентичен debug (сверка по методам и фреймворковым вызовам); на устройстве установленная debug-сборка ведёт себя так же, как release.
- **Шрифты**: в release-APK их переименовывает R8 (`res/HL.ttf` = `dejavu_sans.ttf` байт-в-байт) — `readTypeface` их находит.
- **targetSdk**: 35 и в 1.2.38, и в 1.3.x.
